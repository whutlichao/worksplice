## 负例（内核拒绝，不是 HTTP 层报错）

经 `POST /api/agent/<session>` 的 `{"type":"bash"}`（RPC 面，与工具面共用同一份 operations）：

```
$ curl -o /dev/null -m 5 -w 'http_code=%{http_code}' http://127.0.0.1:30242/api/channels
curl: (7) Failed to connect to 127.0.0.1 port 30242 after 0 ms: Couldn't connect to server
http_code=000
```

```
$ curl -m 5 http://localhost:30242/api/channels | head -c 200
curl: (7) Failed to connect to localhost port 30242 after 0 ms: Couldn't connect to server
```

**同一时刻、同一台机器的人类会话（未沙箱）对照**：

```
human -> http://127.0.0.1:30242/api/channels = 200
human -> http://localhost:30242/api/channels  = 200
```

⇒ 服务在听、人类侧通；成员侧 `http_code=000` 且**连不上**（没有任何 HTTP 状态码，不是 4xx/5xx）。
`localhost` 写法同样被拒 ⇒ deny 不是绑在 IP 字面量上。

**工具面（成员自己发起的）**——让 `port-probe` 用它自己的 bash 工具跑同一条（模型原话）：

```
@port-probe 用你的 bash 工具执行这一条并把输出原样贴出来：
  curl -s -m 5 -o /dev/null -w 'code=%{http_code}' http://127.0.0.1:30242/api/channels

#9 agent:port-probe | 原样贴出（刚跑的这一条）：
    code=000
    curl 自身退出码 0（`-s` 静默了错误信息）；`code=000` 表示连接没建立成功，即 127.0.0.1:30242 在我这个执行环境里不可达。
```

**工具面 vs RPC 面的分离证明（取红）**：把 `lib/bash-containment.ts` 的 `networkRules` 临时回退成票 05 的
`(allow network*)`（一行、带 `[RED-PROBE]` 标记），集成层负例立刻红在主判据上——
「请求根本没到达 app」：真 loopback 服务器的命中计数涨了 1（见 `red-integration-port-07.txt`）。
同一套夹具、只差那条规则 ⇒ 拒绝来自内核规则，不是「端口上没人听」。

## 端口不是硬编码（可验证）

- 沙箱路径上**没有端口字面量**：`grep -n "3014\|3024" lib/bash-containment.ts lib/bash-containment-extension.ts`
  只命中注释里那条实测教训，代码里没有任何端口常量。
- 唯一的端口来源是 `resolveWorksplicePorts` 里的 `env.PORT`（`lib/bash-containment.ts:153`），
  而 `PORT` 由 Next 在 `listening` 事件里写成**真实绑定**的端口
  （`node_modules/next/dist/server/lib/start-server.js:296`；dev 下端口被占自动改端口也写进去）。
- 本次实测的实例跑在 **30242**、封的正是 **30242**：若代码硬编码 30142，结果会正好相反。

## 取证中发现的、与本票无关的一件事（如实记）

`port-probe` 最初几轮 loop 返回 `status: error / reason: "model returned no text (request failed?)"`
（`totals.totalTokens=0, costTotal=0`）——**provider 侧**的失败，不是沙箱：同一时刻同一模型的
秘书回复正常。把该成员的 thinking 从 `off` 改成 `medium` 后同一条 op 立即成功（见正例三）。
