## Question

症状①：频道消息发出后 agent **状态回 online 但无回复**——游标被推进、消息被静默消费。枚举并逐一确认「静默无回复」的完整失效路径，对每个确认的路径给出根因决策并携带修复 + 单测。

**首先把在途未提交改动验证落地为基线**（本 effort Notes 已注明它们是本线的一部分）：
- `lib/agent-loop/loop.ts` `promptSession`：SDK 对模型/API 报错（如 openrouter 402）不 reject `prompt()`，事件流照发 `prompt_done` 但最后一条 assistant 无文本 → 空文本判为 `{ok:false}`（不再静默 ack）。验证它确实覆盖「空文本」场景并补回归测试
- `lib/agent-runtime.ts`：`agent_end`/`agent_settled` 不得把 error 状态洗回 online（error 只被下一次 `agent_start` 清除）
- `lib/rpc-manager.ts`：显式 `initialModel`（§3.10 per-agent runtime）必须覆盖老 session 文件里保存/污染过的模型

**基线之外，逐一排查下列候选失效路径**（每个：复现路径 → 确认手段 → 决策 → 修复）：

- **(a) 空文本的其他来源**：`get_last_assistant_text` 在 compaction 进行中 / 多 stream 交错 / 工具结果后文本未 flush 时是否可能取空，而该轮实际有回复？确认该命令在 `prompt()` 返回后的时序保证；若存在竞态，决定取文本的可靠方式
- **(b) parseAgentAction 误判为空/ignore**：模型输出退化（夹带 `<|eom|>` 等）时 JSON 提取失败 → 整段当 content（不空）；但模型可能协议性回 `{"action":"ignore"}` 且无 content → ack 无回复。区分「正常协议选择」与「误判」；若模型在弱 prompt 下高频 ignore/空，决定 prompt 是否补强
- **(c) 游标过度推进吞掉触发消息**：backfill（崩溃窗口语义：标记存在即推进游标）或并发轮把 `consumed_seqs` 推到触发消息的 seq 之上 → 下次 wake `drain` 空 → noop 无回复。确认 backfill 推进的 seq 是否会越过 agent 实际没回复的轮次；若会，决定推进语义的修正
- **(d) session 忙判定面**：`isRunning()` = `promptRunning/isStreaming/isCompacting/isBashRunning`；driver 的 `waitForSettle` 只监听 `PROMPT_DONE_EVENTS`。extension 注入轮次/其他运行态是否漏判，导致 hint 被「busy 等待」或静默丢弃

## Notes

- 涉及文件：`lib/agent-loop/loop.ts`、`lib/agent-loop/backfill.ts`、`lib/rpc-manager.ts`、`lib/agent-runtime.ts`

## Answer

### 基线落地（在途改动验证为基线，全部已带测试）

- **`lib/agent-loop/loop.ts` `promptSession` 空文本=失败**：验证了 SDK 路径——`handleRunFailure` 在模型/API 报错（如 openrouter 402）时不 reject `prompt()`，而是提交一条**空文本 assistant 消息**（`stopReason:"error"`）；`getLastAssistantText` 只跳过 `aborted`+空 content 的消息，错误轮返回 undefined → 空文本判 `{ok:false}` 可靠，不再静默 ack。回归测试：`a model failure that resolves with empty text (SDK 402) errors without advancing the cursor`
- **`lib/agent-runtime.ts` error 状态保留**：`agent_end`/`agent_settled` 不再把 error 洗回 online（error 只被下次 `agent_start` 清除）。回归测试：`a late agent_end does not wipe the error status of an empty-text failure`
- **`lib/rpc-manager.ts` initialModel 覆盖老 session**：`hasExistingMessages && !initialModel` 才保留文件内模型，显式 per-agent runtime 配置必覆盖。

### 候选路径逐一确认

- **(a) 空文本的其他来源 —— 无竞态，无需修复**。时序验证：`runAgentLoop` 里 `message_end` 先把最后一条 assistant 消息 push 进 `this.messages`，之后才发 `agent_end`、`agent.prompt()` 才 resolve，wrapper 的 `prompt_done` 在其后——`get_last_assistant_text` 读到的是已提交的最终消息。终止保证：runAgentLoop 在工具调用后会 `continue()` 直到非工具消息，**最终 assistant 消息必非纯工具调用**（无纯工具调用收尾的空文本误判）。多 stream 交错由 wrapper `promptRunning`/`inner.isStreaming` 守卫（并发 prompt 直接抛错 → prompt_error → error 不 ack）。
- **(b) parseAgentAction 误判 —— 修复**。区分「正常协议选择」与「误判」：显式 `{"action":"ignore"}` 是合法选择，游标照常推进（保持既有语义与测试）；**`{"action":"reply"}` 无 content（模型退化 JSON）按本轮失败处理**——与空文本同语义：publish error、不推进游标、触发消息保持 pending 供下次 wake 重试。revise 分支同类细化：重写也产出空内容时不推进游标（`ackSeq: input.baseSeq`）。prompt 补强一行（reply 必须携带非空 content）。回归测试：`a reply action with empty content (degenerate JSON) errors without advancing the cursor` + `an explicit ignore with a pending trigger still advances the cursor`
- **(c) 游标过度推进吞触发消息 —— 无需修复**。验证：`scanSessionReplies` 的 flush 门禁只在「该标记轮解析出 reply 内容」时产出条目，`backfillAgentReplies` 只对产出条目的 markerSeq 推进游标——空文本轮 / ignore 轮 / 崩溃无回复轮都不会被 backfill 推进，消息保持 pending。并发轮 ack 只动本 target 游标（channel 与 thread 各为独立 seq 空间）。崩溃窗口「prompt 已入上下文但无回复」的轮次：游标停在标记 seq 之下，下次 wake 重试重读。
- **(d) session 忙判定面 —— 两个真实缺口，已修复**。① `waitForSettle` 只监听 `PROMPT_DONE_EVENTS`，而 `isRunning()` 含 `isCompacting`——manual/extension 触发的 compaction 只发 `compaction_end`（不发 prompt 收口事件），busy 等待**永久挂起**，hint 不丢但也永不重试；修复：新增 `SETTLE_EVENTS = PROMPT_DONE_EVENTS ∪ {compaction_end, auto_compaction_end}` 供 waitForSettle 监听。② busy 判定与订阅之间的竞态窗口：会话在判定后、订阅前收口，settle 事件发在无人监听时；修复：**订阅后复核 `session.isRunning()`，已空闲立即重试**。回归测试：`a busy session stuck on compaction retries on compaction_end` + `a session that settles before waitForSettle subscribes still gets retried`

### 关联

- **BusyCwdError → error 轮被 driver 丢弃（hint 永久丢失）**：确认存在，属 02 范畴（`runAgentRound` 把 startSession 抛错 catch 成 error、driver 只对 busy 重试）——本 ticket 不修，02 决策一处理。
- 「extension/queued 消息」补查：extension 命令执行期间 wake → `isRunning()` 漏判 → 并发 prompt 被 SDK 抛 "already processing" → prompt_error → error 不 ack → 消息保持 pending（非静默消费）；steer/followUp queued 期间 `promptRunning=true` → busy → settle 后重试，均无静默消费路径。
