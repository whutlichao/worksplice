## Question

症状③：唤醒面过宽。`notifyMessageWakes`（`lib/agent-loop/wake.ts`）在消息落库后：
- 唤醒目标 channel 的**全部 agent 成员**（除作者、静音者）→ 一条消息触发多个 agent 各自跑一轮完整 LLM → 刷屏/重复劳动
- 任务线程消息（`target_id` = 锚点）也唤醒**全部频道成员**，只有「任务 owner 自醒续工」分支按 owner 定向 → 无关 agent 插进任务线程答非所问

**决策：默认唤醒策略。**
- 全量唤醒是否收窄为：仅 `@mention` 目标 + 任务 owner（自醒续工）+ 显式唤醒（如提醒作者）；普通频道消息不默认唤醒全员
- 若收窄，与 inbox 的**可见性**语义如何一致：加入 channel = 订阅全部消息（drain 可见）≠ 被唤醒（注意力信号）。当前「加入即唤醒」把两者绑定，收窄后 agent 可能错过「该看但没点名」的消息——是否引入频道级唤醒开关/`@all` 显式唤醒，还是接受「被点名才行动」
- mute 语义联动：现有 §3.2 静音挡普通消息、个人 @mention 穿透——收窄后与 mute 是同一轴的收口还是两套开关

## Answer

### 决策（两轮 grilling 收敛）

- **唤醒面不收窄**（用户明确）：channel 与 thread 消息均维持全量唤醒（除作者/静音者 + @mention 穿透 + 任务 owner 自醒/提醒/秘书定向）——`lib/agent-loop/wake.ts` 分发逻辑零改动
- **回应与否下放 agent 自判**：修的是判断标准不是唤醒面——`buildReplyPrompt` 新增回应 rubric（判断标准），此前 prompt 对回不回应只有一行 `"ignore" says nothing`，模型被唤醒后默认倾向 reply（刷屏/无关插话的模型侧根因）
- **确定信号 = 代码兜底**：被 @mention、或进行中任务 owner 收到线程内他人消息——此类轮次 ignore 不合法：按失败处理（error 状态点、不 ack、触发消息保持 pending 供下次 wake 重试）；同一 (agent, target) 连续失败达 2 次 → cap-ack（游标推进）并记 error log，防模型系统性 ignore 造成的永久 pending + 无限重试
- **术语四词入 CONTEXT.md**：订阅（加入 = drain 可见）≠ 唤醒（触发一轮的注意力信号）≠ 点名 @mention（确定信号，必须回应）≠ 退订 mute（连可见性都挡）；「唤醒 ⊂ 订阅 的信号子集」；mute 与回应判断正交
- **可观测性 fog 毕业**：状态点区分「已回复 / 自判 ignore / 失败」→ 新 ticket 07（自判模式下 UI 无从分辨「看了决定不理」vs「没处理」）

### 修复落地

- `lib/agent-loop/loop.ts`：
  - `buildReplyPrompt` rubric 四行：MUST reply（被点名/任务 owner 收到线程他人消息/提醒/直接提问）、MAY reply（与角色/工作区/当前工作相关）、MUST ignore（他人任务线程、进度播报、无关闲聊——不插话；点名压倒一切）
  - `hasMustRespondSignal` + `MUST_RESPOND_FAILURE_CAP = 2` + globalThis 连续失败计数（`__workspliceMustRespondFailures`，热重载安全）；成功轮（delivered / 任务操作 / 无信号 ignore）重置计数
  - ignore 分支：无信号 → 照旧 ack + ignored（既有语义不变）；有信号 → 失败（不 ack、error）；达 cap → ack + error + reset
- 测试：`lib/agent-loop/loop.test.mjs` 新增/更新 4 条——mention+ignore 失败不 ack 不 join（改写旧「ignore 不 join」测试，旧语义被兜底取代）、连续 2 次 cap-ack、成功回复重置计数（跨轮 streak 语义）、prompt 含 rubric；`lib/agent-loop/loop-tasks.test.mjs` 新增 1 条——任务 owner 线程他人消息 + ignore = 失败且线程游标不推进
- 既有「无信号显式 ignore 照常推进」语义不变（回归测试原样通过）
