现状 ChannelView 3117 行 · 11 概念/屏 目标 ≤4 概念/视图 三栏骨架保留 秘书引导纳入
维度现状A · Focus ModesB · Guided Journey ⭐ 推荐首版C · Minimal + Drawer
中央一次呈现概念数11（消息+引用+任务List/Board+提醒+reaction+ pinned+附件+线程+AsTask+mention+轮询）3（Discuss/Track/Review 三档，每档 3–4）4（消息流为主）+ 顶部旅程条 + 空状态引导，reaction/pinned/附件收进「···」2（仅消息流+Composer），其余全进抽屉
任务板可达性同屏常显，挤占消息Track 模式全屏，消息与任务互斥聚焦Tab 仍在，但默认 Discuss；有任务时 Tab 上 badge 引导切换抽屉内，需一次点击才见
新手路径 describe→hand off→let it run→review无引导，需自行发现 As Task / 任务板 / thread三模式即路径隐射，但仍无显式引导旅程条 4 步常显 + 强空状态卡片（“描述任务”“转为任务”“等待运行”“去审查”）路径被抽屉藏起，需探索
术语友好Board/List、pinned/reaction 等直出Discuss/Track/Review 更通用保留 channel/任务但文案口语化（“讨论”“跟踪”“复核”）同 B
改造成本—中高（ChannelView 拆 3 视图 + 状态切换）低（在现有三栏上加旅程条+空状态+折叠）中（抽屉交互+手势）
与秘书联动无可在 Review 加秘书总结空状态首卡即秘书入口：无 channel/agent 时“让秘书帮你搭第一间房”一键走五步流同 B

结论：采用 B，A 为演进方向，C 否决。 B 在保留三栏骨架与现有路由薄封装的前提下，以最低成本把 11 概念压到 4 以内，且把关键路径做成可见的进度； A 的三模式更彻底，适合重构第二期（06 目标架构落定后将 ChannelView 拆为三个深模块时一并做）；C 把任务藏得过深，违背“任务是协作主实体”的产品定位。 秘书联动纳入首版：首访空状态即秘书五步流入口，完成“建频道+建 agent+发首条消息”闭环。
