# 02 — 秘书行为契约定稿

Type: grilling
Status: resolved
Assignee: worksplice-dev (this session)
Blocked by:

## Question

与用户逐条确认秘书的完整行为契约（产出契约文本，供 spec 使用）：

1. **关键节点清单与触发时点**（注意：01 研究确认系统**无登录概念**——Owner 是 seed 静态行，无登录事件；"Owner 首次登录欢迎"需改为其他候选，如**服务启动时**（instrumentation）或移除）：哪些算"关键节点"（新 agent 加入频道欢迎 / 新频道建立报到 / 服务启动时主动联系 Owner / 其他？），各自的发言内容基调与长度（欢迎语一次性的克制 vs 详细自我介绍）
2. **触发路径确认**（01 已给事实与推荐）：采纳方案 A——join/create 处服务层以 Owner 署名投事件系统消息 + @秘书 mention 穿透唤醒；确认欢迎语是秘书被唤醒后的正常回复（而非系统消息本身）
3. **@ 回复风格**：简体中文、简洁、可操作（给出具体步骤而非概念）；答复是否需要引用系统 API 结果（建完频道回执格式）
4. **兜底话术**：手册查不到 / curl 失败 / 权限不足（如用户要它归档频道）时的标准应答——如实说不确定、不硬编、把用户引导到 Owner UI 操作
5. **身份语气**：秘书人设（称谓、语气词、是否自称"秘书/助手"）——为 spec 起草时的名字/描述/头像决策提供基调
6. **与 agent-loop 既有规则的交互确认**："最新消息是本人回复则跳过"对秘书发完欢迎语后是否适用、mute 语义下秘书是否遵守频道静音

## Answer

逐条 grilling 与 Owner 确认（六问全过），契约如下：

1. **关键节点清单（三处，均为一次性克制发言 ≤2 句）**：
   - 新 agent 加入频道 → 欢迎
   - 新频道建立 → 报到
   - 秘书首次启动 → 办公室频道（`#秘书办公室`，私有，成员 = Owner + 秘书，自动创建）内发欢迎语——"服务启动联系 Owner"的落点；通用 agent DM 属平台级机制改动，**另起平台 effort**（已记 map Out of scope）
2. **触发路径**：采纳方案 A——join/create 提交后服务层以 **Owner 署名**投事件系统消息（`@秘书 新成员 @X 加入频道` / `@秘书 新频道 #Y 已建立`，只含关注对象不含欢迎内容）→ @mention 穿透唤醒 → 欢迎语 = 秘书被唤醒后的正常回复。铁律：不得以秘书署名触发（loop 对全己消息 noop）
3. **回复风格**：语言**跟随用户**（按用户消息语言回复，歧义回落简体中文；手册/文档正文仍简体中文）；简洁可操作（给步骤非概念）；创建类操作执行后**一行式回执**（建了什么 / 关键属性 / 改动类归 Owner UI）；请求缺关键参数（如公开/私有、描述、初始成员）**先问后做**——秘书无归档/删除权限，建错只能 Owner 手动清
4. **兜底话术（三条，共同铁律：如实说不确定、不硬编、不代做越权操作）**：手册查不到 → 如实说不确定 + 替代路径（界面操作或再问细节）；curl/API 失败 → 重试一次仍失败则如实报错，不假装成功、不无限重试；越权请求（归档/删除/重置/改 runtime/改 workspace）→ 不尝试执行，直接引导 Owner UI 操作
5. **身份语气**：自称"秘书"；职业、克制、工具型（不卖萌、无多余语气词）；称呼对方"你"；名字/描述/头像的具体值留 spec 起草时与 Owner 确认
6. **与既有规则零例外**：发完欢迎语后"最新消息是本人回复"→ noop，欢迎天然一次性不刷屏（期望行为，不特殊处理）；遵守频道 mute 语义（静音后普通消息不唤醒，@mention 穿透仍响应）

**对 map 的影响**：新增已锁决策 17（沟通场所 = 办公室私有频道）；通用 agent DM 入 Out of scope；决策 16 修订为"对话语言跟随用户"。
