**实现决策**

- 「有消息」信号采用推荐方案一（零 Store 契约扩展）：`listChannelsWithMeta` 返回值附 `messageCount = getDb().maxSeq(channel.id)`。消息 seq 单调自 1、不可变无删除，`maxSeq > 0` ⟺ 有顶层消息，与 01 迁移删空 DM 的「空」判定（无 `target_id = dm.id` 顶层消息）严格同源。
- `ChannelWithMeta` 接口（`components/ChannelView.tsx`）与 `listChannelsWithMeta`（`lib/domain/raft/channels.ts`）各补 `messageCount` 字段；字段经 `/api/channels` JSON 直通 AppShell → WorkspaceSidebar，无需 route 改动。
- `WorkspaceSidebar.tsx` 的 `dmChannels` 在 `type === "dm"` 之后追加 `.filter((c) => c.messageCount > 0)`；普通频道分组不动。
- 软删归档 DM 零改动：`deleteAgent` 已归档（`archived=1`），`messageCount > 0` 仍为真 → 照常渲染，`ChannelRow` 既有「已归档」标记自然生效。

## Answer（bugfix：发送后侧栏私信即时出现，不依赖 agent 回复 / 15s 轮询）

**根因**

- 服务端 `/api/channels` 的 `messageCount`（= `maxSeq`）在发送后立即正确（实测返回 1）；侧栏 `dmChannels` 的
  `messageCount > 0` 过滤也正确。断点在前端信号传播：`ChannelView` 发送消息（`useChannelData.send`）成功后
  **不回调 AppShell** 更新 `channels.messageCount`——AppShell 只在 15s 轮询 merge 与 `load()` 时刷新该字段。
- 实测（ego-browser 计时）：owner 发送首条消息 → agent 回复约 +8s 到达 → 侧栏 DM 行在 **+14.7s（恰好是 15s 轮询
  tick）** 才出现，晚于回复——即用户观察到的「直到 agent 回复才出现」（二者同乘 15s 轮询，回复只是让轮询同时
  带上 unread 变化，观感上像回复触发）。

**修复**

- `components/ChannelView.tsx` `handleSend`：发送成功（`sendMessage` 不抛 held）后调用 `onChannelChanged()`——
  与 `runChannelAction`（join/leave/archive）同模式的「UI 变更 → 上抛 shell 刷新」，触发 AppShell `load()` 重拉
  channels/members，`messageCount` 随服务端事实即时传播到侧栏。thread 回复不走该路径（thread 有独立 seq 空间，
  不改 channel `messageCount`）。
- `lib/channel-list.ts`（新，纯模块）：`shallowEqualChannel` + `mergeChannelRows` 从 AppShell 抽出——
  `load()` 的「整体替换 + 未变更行保持对象引用」合并语义纯函数化，回归测试可直接锁定「发送消息 → messageCount
  信号传播」。行为零变化（`load()` 内联 merge 原样迁移）。

**回归测试**

- `lib/channel-list.test.mjs`（4 条）：`mergeChannelRows` 传播 messageCount（0→1）/ 未变更行复用旧引用 /
  新行并入 / `shallowEqualChannel` 感知 messageCount 变化。
- `components/ChannelView.test.mjs`（+1 条源码断言，沿用票 03 route 源码级断言先例）：`handleSend` 回调体在
  `await sendMessage(` 之后调用 `onChannelChanged()`。
