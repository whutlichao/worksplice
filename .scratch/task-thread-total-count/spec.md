# Task 讨论回复总数与未读标记

## Problem Statement

旧设计 `.scratch/task-thread-navigation/spec.md` 的 D3 把 Task 锚点「打开任务讨论」按钮上的数字定义为未读回复数，D4 也把锚点徽标解释为未读回复数。用户最新截图显示：普通消息 thread 有 5 条回复，Task 讨论入口却显示 0；数字随已读而归零，无法表达 Task 讨论实际有多少回复。用户已明确重开这一裁决：Task 锚点主数字应与普通 thread 数字同义，表示回复总数，而不是未读数。

本设计重新界定 Task 锚点上的总回复数与未读回复数，同时保留既有的 Task 已读游标、侧栏未读 Task 数和未读总览/筛选。旧设计与已完成 Ticket 03 / 04 的历史记录保持原样；本文件明确记录被新裁决替代的范围。

## Solution

- Task 锚点的讨论按钮显示该 thread 的回复总数：只计回复、不含锚点；任何作者的回复都计入，包括 Owner；已读状态不影响总数。
- 回复总数始终显示，包括 `0`；讨论按钮始终存在，能直接打开对应 Task thread。
- 未读回复数不再占用总回复数字的位置，而是在锚点上以独立的「未读 N」标记呈现。总回复数与未读回复数各自表达不同单位。
- Task 总回复数与「未读 N」在频道可见时每 3 秒刷新；即使频道主消息序列没有变化，Task thread 回复变化也要反映到这两个数字。普通消息 thread 的既有计数刷新行为不在本设计范围内。
- 既有 per-Task 已读游标、侧栏未读 Task 数、未读 Task 总览与筛选、打开 thread 后推进对应已读位置等行为全部保留。总回复数不因打开讨论或读取回复而减少。
- 锚点按钮的无障碍名称分别说明 Task 编号、回复总数、未读回复数及打开讨论的动作；不得把总回复数读成未读数。

## User Stories

- 作为 Owner，我能从 Task 锚点看出讨论共有多少条回复；已经读过的回复仍计在总数里。
- 作为 Owner，我能同时辨认一个 Task 有多少条总回复、其中有多少条未读回复，不会把两种数字混为一谈。
- 作为 Owner，我能从侧栏未读 Task 数、未读总览或筛选定位待读讨论；打开一个 Task thread 只推进该 Task 的已读位置。
- 作为 Owner，即使 Task 尚无回复，我仍能看到 `0` 并通过稳定的按钮打开讨论。
- 作为使用辅助技术的 Owner，我能听到 Task 编号、总回复数、未读回复数和按钮动作各自的含义。

## Implementation Decisions

| ID | 决定 | 用户选择与依据 |
|---|---|---|
| D1 | **Task 锚点主数字 = thread 回复总数。** 统计范围是锚点对应 thread 内的所有回复；不含锚点本身，不按作者筛选（Owner 回复也计入），不按 read position 筛选。已读或未读不会改变总数。 | Q1（人定）：与普通 thread 数字同义，符合最新截图中普通 thread 显示 5、Task 讨论也应显示消息数量的要求。 |
| D2 | **Task 计数按 3 秒独立刷新。** Task 总回复数和「未读 N」在频道可见时都按 3 秒节奏更新；即使频道主消息序列没有变化，thread 回复变化也要更新这两个计数。普通消息 thread 计数继续保持现有刷新行为，本设计不扩展到普通 thread。 | Q2、Q5（人定）：Task thread 变化后数字不应等待频道顶层消息变化；仅刷新 Task 计数，避免扩大本次裁决范围。 |
| D3 | **未读状态保留且单独显示。** 未读回复仍按原 Task 独立已读位置计算；锚点另显示精确的「未读 N」，与总回复数分开。侧栏未读 Task 数仍按有未读回复的 Task 数计算；未读总览/筛选与原有打开、标读规则不变。 | Q3、Q3a（人定）：保留现有未读能力，并用独立精确数字承载未读信息；理由是保留 Ticket 03 已交付的信息，同时让主数字始终表示总数。 |
| D4 | **零回复仍显示入口与数字。** 讨论按钮始终存在；尚无回复时主数字显示 `0`。 | Q4（人定）：入口位置稳定，零值语义清楚。 |
| D5 | **无障碍名称区分两个计数。** 名称要说明 Task 编号、总回复数、未读回复数以及打开讨论动作；`0` 也按总回复数播报。 | Q4、Q3a（人定）：辅助技术用户需要分别获知总数和未读数，不能只依赖视觉位置或颜色推断单位。 |
| D6 | **只取代旧 D3 / D4 的 Task 锚点数字语义。** D3 的按钮稳定存在、Task 编号/状态、键盘可达与焦点要求继续有效；D4 的未读定义、频道与 Task 未读分离、侧栏计数单位继续有效。 | 最终共享理解确认（人定）：保留旧设计中仍有效的部分，不改写已完成 Ticket 03 / 04 的历史记录。 |

### 计数单位

- **回复总数**：Task 锚点对应 thread 中的全部回复条数；包含 Owner 回复，不含锚点。阅读操作不会减少它。
- **未读回复数**：按既有 Task thread read position 统计作者非 Owner 且位于该 Task 已读位置之后的回复条数。打开该 Task thread 仍只推进它自己的已读位置。
- **未读 Task 数**：侧栏中至少有一条未读回复的 Task 数，不是回复条数。

三个数字分别回答「这段讨论有多少回复」「我还有多少回复未读」「有多少个 Task 有未读讨论」，互不替代。Task View 的未读筛选、未读回复数、排序、状态分组/列与原票据保持一致；本设计不把总回复数扩展为 Task 卡片上的新数字。

## Testing Decisions

本票是设计票，不运行测试、不做双轴 code-review 或浏览器验收，也不修改产品源码。未来实施票至少验证：

- 只新增 Task thread 回复时，锚点总回复数增加；Owner 回复也计入，锚点本身不计入。
- 对回复进行已读推进只改变独立的未读 N，不改变总回复数；未读状态仍按作者与该 Task 的已读位置判定。
- Task 总回复数与未读 N 在频道可见时每 3 秒更新，即使没有新的频道顶层消息；普通消息 thread 数字仍遵循其现有行为。
- 零回复时按钮与 `0` 同时可见、可操作；无障碍名称分别播报总回复数与未读回复数（均为零）。
- 侧栏未读 Task 数、未读总览/筛选、单 Task 标读、持久已读位置、Owner 自己的回复排除规则及 Task 状态行为均不回归。

## Out of Scope

- 不修改产品源码、数据结构、迁移、测试或运行时数据；不在本票运行测试、typecheck、lint、双轴 code-review 或浏览器验收。
- 不改变 Task 已读游标、历史已读基线、前台打开期间自动标读、侧栏未读 Task 数、未读总览/筛选及 Task View 结构。
- 不改变普通 Channel 未读或普通消息 thread 计数的定义与刷新行为；特别是本票不处理普通 thread 数字在仅有 thread 回复变化时可能出现的既有滞后。
- 不把 Task 总回复数扩展到 Task View 卡片，不新增通知、批量标读、状态变化或其他未读语义。
- 不改 `.scratch/task-thread-navigation/spec.md`、Ticket 03 或 Ticket 04 的原始内容；本文件与 ADR-0017 作为后续裁决记录其有限 supersession。

### 本轮访谈与 frontier

本轮每个决定均通过 `orchestration ask` 交由用户确认。Q→A 与理由（均为**人定**）如下：

| Q | 答复 | 理由 |
|---|---|---|
| Q1 | Task 主数字是 thread 回复总数：不含锚点、包括所有作者（Owner 也计入）、不受已读状态影响。 | 与普通 thread 数字同义；最新截图中普通 thread 为 5，Task 讨论也应显示消息数量。 |
| Q2 | Task 总回复数按每 3 秒节奏刷新，thread 回复变化即更新，即使频道主序列未变。 | 新回复后主频道上的数字不应滞后，并与可见刷新节奏一致。 |
| Q3 | 保留 Task 已读游标、侧栏未读 Task 数、未读总览/筛选；总数与未读状态分开。 | 满足总数可见诉求，同时不丢现有未读能力。 |
| Q4 | 按钮始终呈现，零回复显示 `0`；无障碍名称说明 Task 编号、总回复单位与打开动作。 | 入口位置稳定且数字语义清楚。 |
| Q3a | 锚点同时显示精确、独立的「未读 N」，无障碍名称也分别说明总回复数和未读回复数。 | 保留 Ticket 03 已交付的精确未读信息，不让主数字被误读为未读数。 |
| Q5 | 每 3 秒独立刷新只适用于 Task 总回复数与未读 N；普通消息 thread 计数保持现有刷新行为。 | 本次只重开 Task 锚点数字，避免扩大到普通消息线程。 |

最终共享理解确认中，用户修正了最初 Q2 的范围，明确普通 thread 计数不在本票修改，并确认该修正后的方案准确、设计树 frontier 清零。没有未回答的产品决策。此前在第一张截图歧义下选择「保留未读回复数作为主计数」的旧回答，已被用户最新截图说明及本轮明确选择取代。
