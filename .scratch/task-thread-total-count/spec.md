# Task 讨论回复总数与未读数分离

## Problem Statement

主频道中，普通消息线程入口显示回复总数，而 Task 锚点的“打开任务讨论”入口显示未读回复数。Task 讨论一旦读过，主数字就可能变成 0，无法回答“这段讨论共有多少条回复”，也与普通线程旁的数字语义不一致。用户根据截图明确要求：Task 入口的主数字应表达讨论消息数量，而不是只表达未读数量。

## Solution

- Task 锚点讨论入口的主数字表示该 Task thread 的回复总数：不含锚点，包含所有作者（包括 Owner）的回复，不受已读位置影响。
- Task 未读回复数继续存在，但与总回复数分开呈现为独立的“未读 N”。两者单位不同，不互相替代。
- Task 总回复数与未读回复数在频道可见时每 3 秒刷新；即使频道顶层消息序列没有变化，Task thread 的新回复也应更新两个数字。此刷新只针对 Task 计数，不改变普通消息 thread 计数的现有刷新行为。
- 现有 Task 未读游标、打开 thread 后推进对应游标的规则、侧栏未读 Task 数、未读总览与筛选全部保留。
- 讨论入口始终显示且可用；零回复时显示总数 `0`。无障碍名称要分别说明 Task 编号、总回复数、未读回复数与打开讨论动作。

## User Stories

1. 作为 Owner，我想在主频道的 Task 锚点上看到讨论的回复总数，以便不用打开讨论也能知道讨论规模。
2. 作为 Owner，我想让总回复数包含我自己发出的回复，以便它与普通 thread 回复数使用相同口径。
3. 作为 Owner，我想让 Task 锚点本身不计入回复数，以便数字只代表讨论回复。
4. 作为 Owner，我想让已读回复仍计入总数，以便打开讨论或标读后，讨论总数不会错误地变小或归零。
5. 作为 Owner，我想同时看到总回复数和独立的“未读 N”，以便区分讨论规模与尚未阅读的回复数量。
6. 作为 Owner，我想在 Task 回复变化后最多等待一个可见的 3 秒刷新周期就看到两个计数更新，即使频道没有新顶层消息。
7. 作为 Owner，我想在浏览器后台暂停计数轮询、回到前台后继续刷新，以便遵循现有频道轮询的可见性行为。
8. 作为 Owner，即使 Task 尚无回复，我也想看到显示 `0` 的稳定讨论入口，以便随时打开该讨论。
9. 作为使用辅助技术的 Owner，我想听到 Task 编号、总回复数、未读回复数及打开讨论动作各自的含义，以便不会把两个数字混为一谈。
10. 作为普通消息线程的使用者，我想让既有线程计数定义与刷新行为保持不变，以便本次 Task 计数变更不扩大到普通线程。
11. 作为 Owner，我想继续使用原有的 Task 未读侧栏数字、未读总览、筛选与逐 Task 标读行为，以便总数改为常驻读数后仍能发现待读讨论。

## Implementation Decisions

| ID | 决定 | 来源与理由 |
|---|---|---|
| D1 | Task 讨论入口主数字表示该 thread 的回复总数，不含锚点，包含所有作者的回复，已读状态不影响总数。 | grill 设计裁决；用户指出普通 thread 显示 5，而 Task 讨论应显示消息数量。 |
| D2 | 未读回复数与总回复数分开呈现为独立的“未读 N”；既有 Task 未读游标、侧栏未读 Task 数、未读总览/筛选及标读规则不变。 | grill 设计裁决；保留已交付的未读能力，同时避免主数字被误解为未读数。 |
| D3 | Task 总数与未读数在频道可见时每 3 秒更新，即使频道顶层消息序列不变；普通消息 thread 计数维持原行为。 | Q2 与 Q5（人定）；用户明确将独立刷新范围限定为 Task 计数，避免扩大本次变更。 |
| D4 | Task 讨论入口始终显示，零回复显示 `0`；无障碍名称分别说明 Task 编号、总回复数、未读回复数与打开动作。 | grill 设计裁决；稳定入口并清楚表达两种计数的单位。 |
| D5 | 新裁决只取代旧设计中 Task 锚点主数字等于未读数的呈现部分；仍有效的 Task 编号、状态、键盘可达、焦点、未读定义及侧栏计数单位继续保留，Ticket 03/04 的历史验收不改。 | ADR-0017 与 grill 设计票；避免追溯改写已完成工作的记录。 |
| D6 | 复用现有 Task 列表读取及其 3 秒刷新，不新增独立计数读取入口。该读结果已含锚点的线程回复总数与 Task 未读数；刷新时更新这两项计数，保留当前 Task 状态等其他视图数据。 | to-spec seam 决策（人定）；用户选择复用现有读取，减少新接口与维护面。 |
| D7 | Task 锚点的呈现沿用现有消息行与 Task 视图数据组合；Task 总数和未读数应在同一讨论入口明确区分。 | 现有渲染结构与已确认的用户可观察行为；不扩展 Task View 卡片的计数呈现。 |

## Testing Decisions

好的测试应验证 Owner 实际看到、听到或能操作的行为，而不是锁定 CSS class、内部状态变量或轮询实现细节。沿用现有 Task 视图读取、频道数据刷新与消息行渲染测试 seam，不新增服务端读取接口。

- Task 视图读结果的锚点回复总数只计 thread 回复，不含锚点，且 Owner 回复也计入。
- 更新 Task 已读位置会改变独立未读数，但不会改变总回复数；未读仍排除 Owner 回复并遵循该 Task 自己的已读位置。
- 在没有新频道顶层消息时，Task 回复总数与未读数仍会在可见的 3 秒刷新周期更新；普通消息 thread 计数维持现有行为。
- Task 锚点实际渲染出的讨论入口显示总数与独立“未读 N”；零回复时入口仍显示 `0` 并可打开讨论；渲染出的无障碍名称表达两种计数和动作。
- Task 计数刷新遵循现有后台页面暂停、回到前台继续的轮询行为。
- 侧栏未读 Task 数、未读总览/筛选、打开 thread 后推进单 Task 游标、Task 状态及普通消息 thread 计数均无回归。
- 参考现有 Task 数据读取/合并测试与消息行的真实渲染测试；断言文字、元素、无障碍名称及交互，不以 class 名作为产品行为证据。

## Out of Scope

- 不改变普通消息 thread 回复数的刷新行为或计数定义；尤其不在本次修正普通线程仅有 thread 回复变化时可能出现的既有滞后。
- 不在 Task View 列表/看板卡片新增总回复数，不改变卡片上的未读详情或未读筛选。
- 不改变 Task 未读游标、历史基线、作者排除规则、侧栏未读 Task 数、未读总览/筛选及自动标读行为。
- 不新增独立计数读取入口、数据库列或迁移，不改变消息存储、Task 状态、通知或 agent 唤醒语义。
- 不重写原 task-thread-navigation 设计与 Ticket 03/04 的历史内容；本规格承接其后续有效行为，并遵循 ADR-0017 的有限取代范围。

## Further Notes

本规格综合用户确认的 Task 总数口径、独立未读数、零值与无障碍语义，以及本阶段已确认的复用现有 Task 列表读取 seam。旧锚点主数字曾表示未读数；ADR-0017 记录该决定的有限 supersession。用户确认普通消息 thread 的计数刷新不属于本次范围。
