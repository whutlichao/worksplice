# HTTP 走廊的调用者身份：成员面整体移出 HTTP，人类面非 loopback fail-closed

**背景**：worksplice 的 app 自己的 HTTP 面没有调用者身份——进门一律按 Owner 处理（`lib/domain/collab/channels.ts:7` 的 `CURRENT_MEMBER_ID = OWNER_MEMBER_ID`）。而 `POST /api/agent/[id]` 接受任意命令，`{"type":"bash"}` 经 `lib/rpc/session.ts:746` 进入 `AgentSession.executeBash` 的**裸本地实现**（`dist/core/agent-session.js:3037` 的 `options?.operations ?? createLocalBashOperations({ shellPath })`，worksplice 不传 `operations`）。于是任何能摸到端口的东西都能让 app 代它跑一条未沙箱的 shell；同一 Owner 权限面上还有几条同级入口（`/api/plugins` 的包安装 = 在 server 进程里跑代码、`/api/models-config` 写 `models.json`、`/api/auth/api-key/*`、`/api/skills/install`）。ADR-0012 决策六把这条走廊判成排序链第一环：沙箱的归属是「会话归属的成员」，**无归属**的会话不沙箱，而这条路由让调用者**自己挑会话**——沙箱层关不掉它，因为它决定不了「谁在问」。本决策定这条走廊的形态。

**决策一（成员面整体移出 HTTP——身份取结构，不取凭证）**：**app 的协作面整体不再经 HTTP 暴露给成员侧。**① **成员经 HTTP 调 API 没有正当用途**：`docs/spec.md` §5.7 明写「agent-loop 直接调服务层，不走 HTTP」，成员的 drain/reply/claim/complete/ack 全在进程内完成；成员的回复 prompt 里不出现 base URL 与 `curl`；秘书手册 7 条 curl 的只读那一类每轮语境里已经有了，唯一无处可去的创建类是 spec §5.4 的 act 清单**本来就写了**（`schedule reminder` / `react` / `pin`）而实现没跟上的缺口。**所以本决策不是「A 比 B 好」，是 B/C/D 要解决的那个问题不存在。**② **排除凭证类方案的主因（非次要理由）**：成员 bash 与人类**同 uid、同 loopback**，本机没有任何 OS 级手段能区分两者（socket peer credentials 给出同一个值；`Origin` / `Sec-Fetch-Site` 是 CSRF 防御、其前提就是「攻击者是设不了头的浏览器」，成员一条 `curl -H 'Origin: …'` 即破；而**一个调用者必须持有的秘密必然可被那个调用者读到**——它得用那个秘密才能调用）。因此共享密码与 per-agent token 都只能给「可区分」，给不了「挡得住」——**唯一关得掉的形态是「成员够不到的通道」**。③ **形态**：成员需要的系统能力走 **loop 的结构化回复协议**（`parseAgentAction`，今天已承载 `claim`/`complete`/`unclaim`）——创建类操作作为**新 op** 加进来，与既有 op 同一条缝、同一套 freshness 纪律；身份是**结构身份**（`runAgentRound` 握有 `agent`，调用点天然知道它代表谁，不经请求头自述）；**不注册新工具**（工具会动「工具集 = `PRESET_DEFAULT`」这条锁定条目的字面，而 op 什么都不改；`lib/tool-presets.ts` 全程不动）。op 对**全部成员同等开放**（不做秘书豁免），能否执行由协作服务层按调用者身份裁决——判据是「默认拒绝、逐条开口，开口的是不提升调用者权限、只扩大协作面的动作」；人类专属操作（归档 / 删除身份 / 三种 reset / 改 runtime / 改 workspace）不开。7 条能力与旧 curl 速查 1:1 对位，**一条不少**。被否决：强制共享 `WORKSPLICE_PASSWORD`（消灭零配置、给不出身份、且与「不做秘书豁免」冲突——把秘密写进秘书家目录正是 `docs/spec-bootstrap-agent.md:88` 今天这么教的）、per-agent token、分离端口（同 uid 同文件系统，换门不换锁）、三者组合。

**决策二（人类面的准入：loopback 零配置，非 loopback fail-closed）**：**不强制 `WORKSPLICE_PASSWORD`**——loopback 上维持零配置（`npx worksplice` → 浏览器 → 可用），这条姿态由 `.github/SECURITY.md` 的威胁模型背书；`WORKSPLICE_PASSWORD` 的职责**收窄为「非 loopback 的准入闸」，明确不承担身份**。**非 loopback bind + 无凭证 ⇒ 服务不可用**（fail-closed，与 ADR-0012 决策五同构）。事实依据：`npm run dev:lan` / `start:lan` 直接起 `next dev -H 0.0.0.0`，**绕过 `bin/worksplice.js`**，因此今天走 npm 脚本放宽 bind 时**连那条「listening without authentication」的警告都不会打**；而 Host 白名单放行 IP 字面量、非浏览器客户端不做来源校验 ⇒ 局域网内一条 `curl` 即拿 Owner 权限。**「检查放在哪」的决定性理由：只改 `bin/worksplice.js` 会漏掉四条 npm 脚本**，所以判定必须落在服务进程内（`proxy.ts` / `instrumentation.ts` 一类位置），CLI 包装另加第一道明确报错；实施票要取证「`instrumentation.ts` 抛错能否真的阻止 Next 启动」，测不出就如实记为未达成、以请求门为准。

**决策三（env 面与请求面的先后：协调器判断成立，但要重述，且它不是请求面的替代品）**：「env 收口是前置，否则认证自欺」**成立**——只要请求面的门是凭证，而凭证经由 `getShellEnv()`（`{...process.env}`，`dist/utils/shell.js:115-126`）进入每个成员的每个 bash 子进程，成员一条 `env` 就读到了，那道门对威胁模型里的主体完全不成立。**但要重述三处**：① 它不是「请求认证的前置」，是「**凭证渠道**的前置」——它约束秘密怎么发放，不约束请求面收不收（本决策否决了靠凭证的门，但这条前置对将来任何一种靠秘密的机制仍然成立）；② **做了 env 收口不等于请求面收紧了**——请求面的默认姿态是「无认证」，把 env 收口当请求面的替代品是新的自欺；③ 比它更前置的是「成员手里不能有到本端口的 HTTP 客户端」（决策五）。落地取值：**命名空间一刀切剥 `WORKSPLICE_*`，不带成员判定分支**——若写成 `if (是成员会话) 剥`，那么任何一条归属信息缺失的路径就是泄漏路径，而「归属缺失」正是本决策在处理的失效形态；无分支的形式没有这个失效模式。今天这一类里**只有 `WORKSPLICE_PASSWORD` 是秘密**，其余 `WORKSPLICE_*` 一并剥掉按命名空间更省心但别把它们说成秘密。**不要剥 pi 故意暴露的五项**（`PI_SESSION_ID` / `PI_SESSION_FILE` / `PI_PROVIDER` / `PI_MODEL` / `PI_REASONING_LEVEL`——pi 的 bash 工具 guideline 明确告诉模型可以读它们）。接缝：bash 工具面有 `BashToolOptions.spawnHook`；RPC 面**没有** spawnHook（`executeBashWithOperations` 不传 `env`，落 `env ?? getShellEnv()` 的兜底），唯一杠杆是 `operations` 包装（`executeBash(command, onChunk, { operations })`）——**一个包装过的 `operations` 同时盖住两个面**，而 ADR-0012 的沙箱也落在同一处，「这个子进程能拿到什么」因此只有一处答案；包装必须总是显式构造 env，不能写成「上游给了就转交」。

**决策四（`{"type":"bash"}` 那条执行入口由谁把守：不加第二道身份门）**：这条入口的调用者有三种，守卫分属两票——**人类（浏览器 `!bash`）**属 ADR-0012 实施票（决策三：沙箱跟随会话归属的成员，无归属会话不沙箱）；**成员（被注入后的 curl）**属本决策的「成员 → 端口关闭」（沙箱落地前靠 ADR-0012 决策五「无沙箱不激活 bash」⇒ 成员手里没有 HTTP 客户端；落地后靠内核按端口过滤）；**成员会话被他人指名**同上，因为无归属会话不沙箱，所以守卫**不在它身上**，在「成员能不能到门口」上。**结论：这条入口上不加第二道身份门**——本机没有能区分「人类 curl」与「成员 curl」的手段，任何加在这里的门只能加在凭证上，而凭证对成员无效；**加一道无效的门比没门更坏**，因为后来者会以为它已被守住，于是放松「成员 → 端口」这一层的持续维护。**它靠的是门口没有成员，不是门上有一把锁。**代价写明：在「成员 → 端口关闭」完成之前这条入口对成员**是敞开的**，本票不声称收口了它，沙箱票也不能（ADR-0012 决策六原话：只能自述为「纵深防御的一层」）——**两票合起来才收口**。

**决策五（排序链与 fail-closed 原则的耦合）**：时间轴四条——① env 收口（独立前置）；② 成员能力面与协作面整体移出 HTTP（**解锁 ③ 的后半**）；③ 成员 → 本端口关闭（两阶段，各有一条支撑、没有空窗：沙箱落地前靠 ADR-0012 决策五、落地后靠内核端口过滤）；④ 人类面 loopback 零配置 / 非 loopback fail-closed。**②解锁③的理由**：ADR-0012 的 Further Notes 记了那条按端口过滤**可用**但**本形态不使用**，唯一理由是「**因为秘书的 curl 能力面是锁定条目**」——本决策的 Q4 裁定（锁的是能力面不是通道）之后该理由消失，**端口过滤成为可用形态**；这是本决策对 ADR-0012 的唯一后果性影响：不是重开它的六条决策，而是它自己留下的那条保留**因本决策而解除**（ADR 追加式记录，不改旧 ADR 正文）。**「拿不到安全前提就不提供服务」这条原则现在被三处引用**：ADR-0011 决策六第三条（判定自身出错一律拒绝，已合入）、ADR-0012 决策五（无沙箱不激活 bash，**coordinator 代答、仍待人类追认**）、本决策决策二（非 loopback 无凭证拒绝服务）——**若人类推翻这条原则，三处都要改**；尤其 ADR-0012 决策五一旦被推翻，「成员没有 HTTP 客户端」这条不变量的前半段同时失效，收口被推迟到沙箱落地之后。

**Consequences**：

- 本决策收口的是「成员能不能把 app 当成一台以人类权限运行的控制台」，不是「成员看不到哪些数据」。首要残留是 ③ 完成前的窗口（成员仍有 bash ⇒ 仍有 HTTP 客户端 ⇒ 整个 Owner 权限面对它敞开），且 ③ 的前半段**被人类对 fail-closed 原则的追认阻塞**；其余残留：具备网络能力的扩展 / 包工具（本决策把「成员会话不得激活网络能力工具」升成一条约束，但**不做工具审计**）、同一台机器上用户自己的其它进程（与用户 shell 同权，不在威胁模型内）、人类面在 loopback 上没有准入闸（有意保留）、同 uid 的进程间手段（`kill` / `ptrace`，沙箱 profile 是否拒绝由 ADR-0012 实施票一并定）、env 之外的秘密通道、TOCTOU 与允许根之内的破坏（沿用 ADR-0011 D6）。
- **用户可观察后果**：`npm run dev:lan` / `start:lan` 在未配置凭证时将**拒绝服务**，想要局域网访问必须先设凭证——这是安全默认，但确实改变现有用法。
- 不重开 ADR-0011（注入点、允许根构成、越界处置）、ADR-0012（六条决策）、ADR-0001（家目录两分）、ADR-0007（同一事实不写两处）、ADR-0008（分层方向）。本决策只在 ADR-0012 决策六授权的范围内取值（那张票自己写着「正确形态是给内部调用者受控凭证或专用通道——这是那张票的决策」）。
- 秘书 `[锁定]` 条目的读法：锁定的是**能力面**（bash 可用、curl 可用、7 条命令可用、零配置、base URL 稳定），不是**通道**。追加一条比「不必改」更硬的理由：`docs/spec-bootstrap-agent.md:88` 的「设了 `WORKSPLICE_PASSWORD` 时 curl 加 `-u pi:<密码>`」若照字面实现，等于把 app 的准入秘密**写进成员家目录**——任何「秘密不落进成员可读处」的形态与它**不相容**，这一句必须退休，无论是否换通道。
- 实施票另开（本决策不实施）：env 收口（包装 `operations`）／成员能力面与协作面移出 HTTP（回复协议 op + 服务层调用者参数与授权表 + 秘书手册改写 + 7 条动作回放）／成员 → 端口关闭（两阶段）／非 loopback fail-closed／人类面 HTTP 契约的真端到端测试（今天的 `lib/domain/collab/*-route.test.mjs` 是读源码正则断言，不是真跑 HTTP）。
- 术语「准入闸」「调用者身份」「结构身份」「人类面 / 成员面」入 `CONTEXT.md`；设计全文见 `docs/http-corridor-caller-identity.md`。

**Status**: accepted（Q1 取「成员面整体移出 HTTP」、Q4 取「锁的是能力面不是通道」、Q5 取「非 loopback fail-closed」三条经 `orchestration ask` 回收裁定；Q2 的「不强制凭证、loopback 零配置」与 Q3 的重述为同一次裁定的推论。**两笔挂账已于 2026-10-06 全部销案**——人类确认接受 fail-closed 原则（含 ADR-0012 决策五那条原由 coordinator 代答的政策，代答转正），并接受 `dev:lan` 未配凭证即拒绝启动这一用户可观察后果。三处引用（ADR-0011 决策六第三条 / ADR-0012 决策五 / 本决策决策二）现均为人类拍板，不再有「推翻则三处都要改」的开放风险）
