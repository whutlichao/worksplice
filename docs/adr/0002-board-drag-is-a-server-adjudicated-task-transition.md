# 看板拖拽 = 服务端裁决的状态转移，而非本地视图操作

任务此前只有一种呈现（按状态分组的纵向列表）。新增**看板**视图：列与任务状态一一对应（5 列常显），跨列拖拽卡片即**请求一次状态转移**——落点合法性由服务端状态机（`TRANSITIONS` 转移表 + 授权谓词 + reopened 封锁）裁决，不是客户端视图层面的移动。为此 `TaskView` 新增 `reachable: TaskStatus[]`：服务端按当前身份（UI 唯一操作者 = 人类 owner）推导该任务可发起的转移集合，看板据此高亮可落列、拒绝非法落点（弹回+提示）。claim 是独立操作（`claimTask`），`reachable` 为其合成 `todo → in_progress` 边（reopened 任务仅人类可达，与服务层封锁一致）。

**拖拽不做乐观移动**：松手后卡片留在原列，等服务端确认成功（`updateTaskStatus` 返回）才随轮询/重载落位；失败不动并提示。理由：状态机不是全连通图（如 `in_progress → done` 不存在、`in_review → done` 要求非 owner 批准），非法落点是可预期的常态而非异常路径，乐观移动会频繁"落下去又弹回"。

**Consequences**: 拖拽与卡片动作按钮完全等价——claim/unclaim/reopen 等重语义转移同样由拖拽可达（落点 = 状态机可达即合法），无"轻/重"手势之分；列表/看板切换偏好存 localStorage（默认列表）；看板列 = 状态投影，不引入"自定义泳道/手动排序"概念；`reachable` 由服务端推导，客户端不镜像状态机表，不会漂移。
