# 消息指认用完整消息 id；巡检是任务保洁，不是需求捕手

**背景**：首席是**一个身份、两个职责**（收件人 / 路由者，见 `GLOSSARY.md`「首席 (Chief)」），但两个职责各有半截落在代码之外。① **路由者缺一个句柄**：轮次 prompt 的消息行只渲染 `#seq`，而把消息转成任务的工具（`worksplice_task_create`）参数只要 `messageId`——她读到的每一条消息都给不出工具需要的那个值，于是「这条得有人做」只能换来一段话，落不成任务；搜索观测行同一处缺口，修一个入口等于半边不可用。② **「卡住的事」无人发现**：无人认领的 `todo`、分流失败停在 `blocked` 的、做完等人互审却没人审的，只能靠人自己去翻任务板——任务板是被动视图，不是巡检。本决策定这两处的形态，并明确写下**不做什么**，避免以后被当成遗漏补上。设计全文与逐条取舍见 spec #265。实现：`lib/agent-loop/injection-budget.ts` / `lib/agent-loop/member-ops.ts`（#266）、`lib/domain/collab/patrol.ts` / `patrol-run.ts`（#267）。

**决策一（消息指认＝完整消息 id，唯一渲染点，两个入口同形）**：**凡是她读到的消息都带完整消息 id**，形状只有一处字面来源——`messageIdTag(messageId)` 产出 `(messageId <完整 uuid>)`。**渲染点唯一**：轮次注入的每一行由 `projectMessages` 的行渲染器行尾追加它（`#seq @author: 正文 (messageId <id>)`），decide / revise 两个 prompt 因此自动一致；**搜索命中同形**：`formatSearchObservation` 的消息命中行（频道命中与线程命中）用**同一个函数**加句柄。`InjectableMessage.id` 因此是必填字段（缺 id 的消息进不了注入投影）。**建任务工具的参数形状一字未动**（仍是 `messageId`）——这是本条的直接收益：不需要 seq→id 映射、不需要新的解析函数、不需要在协议里加字段。行首的 `#seq` 保留：seq 是 `react` / `pin` 的句柄且只在自己 target 内唯一，与消息 id 各管一件事，两者并存。**被否决的备选**：① **短 id / 前缀唯一性解析**——省的是几条字符，代价是引入一种新的歧义错误（前缀撞车时要另造一条解析失败路径、还要为「前缀在哪个 target 内唯一」定规则）与一份持续维护的 id 分配面；模型拿错句柄的错误是静默的（建任务建到别的消息上），而这点字符在整轮注入预算里占比极小。② **在注入块顶部给一张 seq→id 对照表**（省行内字符、保持行短）：多一个必须与消息块同步裁剪的结构，且裁剪边界与消息行不一致时对照表会短于实际注入行。③ **只给搜索命中加 id**（改动面最小）：轮次注入是主入口，只修一个入口等于半边不可用。④ **把建任务工具改成收 seq**：seq 在不同 target 之间不可比（thread 有自己的 seq 空间），工具参数会退化成 `(target, seq)` 二元组，且既有 UI / HTTP 契约都以消息 id 为准。**归档命中不在此列**：它是 session 归档条目、没有频道消息 id，保留自己的 archive / entry 定位，**不硬造一个不存在的 messageId**。

**决策二（巡检是任务保洁，不是需求捕手）**：巡检（`lib/domain/collab/patrol.ts` 判定层 + `patrol-run.ts` 接入层）只处理**已有任务**的三种卡住，每分钟一次、有界：未认领的 `todo` 超过 `PATROL_UNCLAIMED_TODO_MS`（30 分钟）、`handoff_state = blocked` 超过 `PATROL_HANDOFF_BLOCKED_MS`（30 分钟）、`in_review` 超过 `PATROL_IN_REVIEW_MS`（24 小时）；只往回看 `PATROL_WINDOW_MS`（7 天）内**创建**（锚点消息时间）的任务，卡住时长按任务行 `updated_at` 算。判定层是**纯函数、零 IO**（时间 / 任务快照注入），去重签名 = (任务, 状态, 详情)**不含时长**——**状态变化才重报，不按时间冷却**（冷却会把「状态变了」一起吞掉）。输出每轮**最多一条**汇总消息，无发现返回 `null` = 完全沉默（不报「一切正常」）。投递按**系统事件**语义：`wake: false` + `roomNotice: true`。扫描范围 = 全局首席作为成员、未归档、非 DM 的频道；落点见 Consequences 第二条。**它不读消息内容、不建任务、不派活、不改任务状态**（唯一写入是投递）。**被否决的备选：巡检兼做需求捕手**（读频道正文、把口头需求变成任务，再派给人）。理由三条：① **它需要一个本形态不提供的输入**——识别口头需求要读正文并做判断，等于把「她作为收件人时那一轮」的决策搬到定时器里重做一遍，而那一轮缺的只是**句柄**（决策一已经补上），不是「没人定时扫」；同一件事两个触发面必然给出两套判定，且巡检侧没有本轮的人类语境与任务创建事件准入。② **建任务留在巡检里会得到一个没有触发路径的能力**：任务创建是「人类说了什么」的回应，把它挪到分钟节拍上，等于可以由任意历史消息凭空长出任务；而 spec 已把「派给谁」判给消息触发的轮次。③ **判定层会失去纯函数性**：读正文就必然拖进消息读面、mute 口径与可见面判定，逐条测阈值边界与时序的能力随之消失（这三类卡住**恰好只需要任务行的几列**）。同类被否决：巡检自动派活（改 owner）、每发现一条消息（噪音）、时间冷却去重、per-channel / per-agent 开关（先用环境变量）、把巡检做成新 HTTP 路由。

**Consequences**：

- **注入侧的固定开销，不放宽任何上限**：行尾 id 是**固定成本**，注入预算按「含 id 的行」度量——`ROUND_INJECTION_BUDGET_CHARS`（整轮）、`INJECTION_MESSAGE_WINDOW`（条数）、`MESSAGE_CONTENT_CAP`（单条正文）三个上界**一个都没调**。裁剪分支的处理是承重的：**截断只吃正文**，行首句柄与行尾 id 都先占住（`projectMessages` 的截断分支先算 `linePrefix + notice + messageIdTag` 的余量再裁正文）——被截掉的正文可以再搜，被截掉的 id 会让模型**永远**调不对工具（这条有用例钉住）。
- **落点兜底是新引入的语义**：既有代码只回答「谁是首席」（`resolveEffectiveChief`），**不回答「落在哪」**。本决策定：涉及「她是生效首席的频道」的发现优先落在那一个频道 → 否则退到她所在的第一个频道（已加入、未归档、非 DM，扫描列表本身就是这个集合）→ 都没有则静默。不广播、不私信人类。后来者不要把这条兜底当成既有约定（`resolveDestination` 的头注释写着同一条）。**取自源码而非 spec 字面的一处偏差**：spec 写「第一个**公开**频道」，实现取的是扫描列表第一条（`listChannelsWithMeta().filter(joined && !archived && type !== "dm")`，**含她已加入的私有频道**）；文档按实现记录，若将来要收窄成「仅公开」，改判定点在这一处。
- **巡检与房间轮次预算的关系（承重）**：巡检消息若被计成普通 agent 发言，会持续吃掉 `MAX_REPLIES`，把正常对话挤成沉默。所以投递必须 `roomNotice: true`（`wake: false` 亦让 `sendMessage` 的 `recordRoomTurn` 整个跳过）：**不进房间场次、不动迟到名额、不 supersede 在跑场次**，但消息仍然可见。`patrol-run-wiring.test.mjs` 的「系统事件语义：不唤醒任何人、不占房间轮次预算」直接钉住它（发一条巡检后读房间场次快照：`wake` 事件数为 0、`replies` / `epoch` / `lateTurns` 三条都不动）——不要把它改成「普通消息 + 显式 wake」。
- **签名集只在进程内**：去重签名存 `globalThis.__worksplicePatrolSignatures`（`setPatrolSignatureStore(null)` 是测试接缝），**不落库、不加 schema 列**。重启后同一批卡住任务会再报一次——可接受（比多一张表 + 迁移划算）。修好的任务签名随扫描结论一起淡出，之后重新卡住算新事件。
- **阈值可调，但只改判定层**：`PATROL_*` 四个常量只有 `patrol.ts` 一处定义，接入层与测试共用；调阈值不该需要动 `patrol-run.ts` 或任何调用点。默认开、`WORKSPLICE_PATROL_DISABLED=1` 整体关闭（`isPatrolDisabled` **现算**，不在模块顶层求值到常量——进程启动后再设也能生效，测试可直接传 env）。
- **不新增 HTTP 路由、不改任何既有 HTTP 契约**：巡检搭既有每分钟维护节拍（`tickAgentLoopMaintenance`，与到点提醒、handoff 恢复同一分钟节拍），不新起定时器、不注册路由；消息指认只改 prompt 的渲染形状，`parseAgentAction` 协议、`worksplice_task_create` 参数、UI 一概不动。
- **用户可观察后果**：首席在频道里能直接把她读到的某条消息变成任务（当轮即可派出去）；频道里会出现至多每分钟一条的 `Task patrol: N stalled task(s)` 汇总（首日可能报出 7 天窗口内的历史任务——这是窗口生效范围内的预期结果，不是 bug；噪音不可接受时优先调阈值，不要再缩窗口）。
- **测试形状**（后续改动照此写）：判定层逐条测阈值两侧（29 / 31 分钟、23 / 25 小时）、7 天窗口边界、三类各自命中与不命中、签名去重与状态变化重报、空任务集返回空；接入层注入时钟 / 任务快照 / 投递器，断言「无发现不投递」「有发现恰好一条」「落点优先级与兜底」「投递失败不消耗签名」；消息指认侧既有预算测试保持绿。

**Status**: accepted（两个决定由 spec #265 定稿、经票 #266 / #267 落地；术语落 `GLOSSARY.md`「首席 (Chief)」「消息句柄」「任务巡检」「巡检落点」，模块与接入结论落 `AGENTS.md`）
